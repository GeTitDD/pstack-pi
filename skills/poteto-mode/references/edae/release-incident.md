# Release 与 incident feedback

发布前沿用 [Shipping](../../playbooks/shipping.md) 的验证与落地流程。这里补充 Agent 行为证据，不扩大部署授权。

## 发布记录

- 固定候选代码、提示词、工具 schema、模型配置与数据版本。列出基线、候选评估和仍未验证的项目。
- 权限与隔离用例必须通过。质量、失败率、成本、时延采用任务事先确定的阈值，不在看到结果后放宽。
- 写清观察指标、分批范围、停止条件、负责人和回滚到的配置版本。验证回滚是否兼容当前持久化状态，不能只回退提示词。
- 区分本地验证完成、允许发布、实际已发布和发布后观察完成。没有线上证据时不声称生产成功。

## 事故反馈

先按现有事故流程控制影响范围。保存脱敏 trace、配置版本、影响时间线和首次偏离点。推断根因时复用 [why](../../../why/SKILL.md)，运行时调查沿用原有 forensics playbook。

将可复现失败变成固定用例，先证明旧版本失败，再证明修复通过。标记根因为数据、模型、工具、编排、权限或环境，记录仍有争议的解释。仅把得到验证的改进写入结构或测试，避免每次事故都叠加一条全局提示。

事故记录至少包含影响、触发条件、证据、已验证根因、缓解措施、回归用例、发布或回滚决策、后续责任人。无法重放的故障保留缺失信息与补采集计划。
