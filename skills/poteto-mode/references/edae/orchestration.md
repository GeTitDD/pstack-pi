# Orchestration 与恢复

先验证单 Agent 和显式函数调用能否完成任务。只有职责、工具权限或并发收益需要时才增加 Agent。

实现前写出状态转换和持久化边界，例如 pending、running、succeeded、failed、cancelled。明确哪个组件拥有状态，哪个事件允许重试，哪个状态不能再次产生副作用。

- 每个作业、尝试与工具调用有独立身份。交接包含目标、输入版本、产物引用、验收条件、权限与截止条件。
- 超时、重试次数、总调用数、总成本与并发度都有界。记录达到上限后的终态，禁止无限自我修复。
- 同一副作用复用业务幂等键。验证提交成功但确认丢失的情况，不只验证调用前失败。
- 持久化检查点与副作用的先后顺序必须明确。重启后从业务记录恢复，不凭模型摘要猜测事务是否已执行。
- 并发写入先消除共享目标，沿用 [principle-separate-before-serializing-shared-state](../../../principle-separate-before-serializing-shared-state/SKILL.md)。确有共享不变量时验证冲突检测和单一提交者。
- 验证取消后迟到结果、重复投递、旧版本结果和部分成功。明确补偿操作是否需要额外授权。
- 故障注入在隔离环境执行。至少覆盖本次改动触及的重试或恢复窗口，并核对最终状态与副作用次数。

多 Agent 执行继续使用 [swarm](../../../swarm/SKILL.md) 和入口的角色配置。业务 Agent 编排与 pstack 开发子任务是两种用途，不要把开发委派记录当成业务系统的可靠性证据。
